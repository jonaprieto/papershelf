# knowledge-graph

## Summary

Item's identity today is a resolved filesystem path (Hammer.swift:528), not a content hash; the codebase's real content hash (fileDigest, SHA-256 of the whole file) is computed only conditionally, inside same-byte-size groups, for duplicate detection, not as a store key. Marks and notes live inside the PDF itself as PDFKit annotations (Annotations.swift), never in a side file, and RunCache (Cache.swift) is a disposable whole-file JSON overwrite explicitly described in its own doc comment as "a preview, not a claim about the present." SQLite via the system libsqlite3 in WAL mode is the right storage choice for the new store, verified directly on this machine (import SQLite3 compiles and links through the SDK's own modulemap, FTS5 and bm25() both work, WAL gives one-writer-many-readers across processes), and is a strictly smaller and more mechanically verifiable dependency than standing up Core Data/SwiftData for a job Apple's own docs say not to do to a Core Data store from outside its own API.

## Design

STORAGE DECISION: SQLite via the system libsqlite3 (`import SQLite3`), opened in WAL mode, behind a small hand-written wrapper in PDFHammerCore. Rejected: Core Data/SwiftData (clears the macOS 14 floor exactly, but its on-disk format is private by Apple's own documentation, which forecloses the MCP server reading it without also linking Core Data/SwiftData and standing up a full ModelContainer — plus no built-in FTS, and true cross-process access needs NSPersistentHistoryTracking + remote-change notifications, real machinery meant for an app-and-its-extensions, not a GUI app and an unrelated companion process); plain JSON files (RunCache's own model — correct today only because it is disposable; scaled to \"thousands of documents\" with Markdown bodies it means a full-file parse on every read by *both* processes and a full-file rewrite on every watcher-triggered change, with no index and no real full-text search).

WHERE IT LIVES: reuse the exact call already in this codebase —
`FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask).first!.appendingPathComponent(\"PDF Hammer\", isDirectory: true).appendingPathComponent(\"library.sqlite\")`
→ `~/Library/Application Support/PDF Hammer/library.sqlite`, sitting beside (not replacing) `last-run.json`, since RunCache is disposable and this store is not. In WAL mode SQLite adds `library.sqlite-wal` and `library.sqlite-shm` next to it automatically; verified locally. The MCP server, as a separate local process running as the same user, resolves the identical path with the identical API call — no IPC, no shared container ID, no protocol needed for it to see live data; this is the whole payoff of the SQLite/WAL choice over any alternative.

CONNECTION MODEL: open with `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`. Because the system build is \"multi-thread\" safe (sqlite3_threadsafe()==2: one connection must never be touched from two threads at once), wrap the GUI's one read/write connection in `public actor Library`, so every call is serialized onto one execution context by construction; the MCP server opens its own second connection (SQLITE_OPEN_READONLY is the honest declaration of intent for a process that only answers questions) inside its own actor instance. Never let any code reach the raw `OpaquePointer` off-actor — Hammer.swift's existing heavy use of `DispatchQueue.concurrentPerform` for scanning/hashing must feed results *into* the actor via `await`, not touch the connection directly.

IDENTITY: key every document row by `fileDigest(_:)` (Hammer.swift:861-869, SHA-256 of the whole file, already exists, already streams in 1MB chunks, already parallelizable the way `duplicateGroups` already parallelizes it) — but call it *unconditionally* on every newly-seen file at ingest, not gated behind a same-byte-size collision as duplicateGroups does today. `contentKey` (the fuzzy opening-text fingerprint) keeps its existing job of surfacing likely-duplicate content in the UI; it is unfit as a primary key (nil for scans with no text layer, needs passwords, deliberately collision-prone). Cost is linear in total bytes, parallel across files, and — crucially — paid exactly once per unique piece of content ever seen, because a changed file becomes a new row rather than a re-hash of the old one; only the watcher's mtime/size change signal (already read via `contentModificationDateKey`/`fileSizeKey`, Hammer.swift:756-762) triggers a re-hash of a given path.

REAL TENSION TO FLAG: Annotator.save() re-serializes the whole PDF through PDFKit on every highlight/note edit (Annotations.swift:245-261), so annotating a document changes its bytes and therefore its content_hash. A pure content-addressed store would treat every annotation as \"a new document,\" silently orphaning that document's tags/project-membership/notes. Recommended fix: a `documents.superseded_by` column plus a small \"supersede\" step in ingest — when a path's content_hash changes but the new file's page_count/title/author still match the previous row for that path, carry tags/project-membership/document_notes forward to the new hash and set the old row's `superseded_by`, rather than deleting it. This is a heuristic, not a guarantee (flagged under risks); the alternative — hash only the page content and ignore the annotation dictionary — needs a new, more expensive extraction-then-hash pipeline that does not exist today, so it is not the smallest design.

## Verified facts

- Item's stable identity today is a resolved filesystem path, not a content hash: a moved or renamed file gets a different key.
  EVIDENCE: Sources/PDFHammerCore/Hammer.swift:528 — public var key: String { source.resolvingSymlinksInPath().path }

- The only true whole-file content hash (SHA-256, streamed in 1MB chunks) is fileDigest, but it is only computed for files that already collide on byte size with another file in the current scan, not unconditionally for every file.
  EVIDENCE: Sources/PDFHammerCore/Hammer.swift:861-869 (fileDigest) and 935-951 (bySize bucketing before hashing, duplicateGroups)

- contentKey, the other 'sameness' fingerprint, is a fuzzy hash of the first 3 pages' text (SHA-256 of lowercased letters/digits), not a content-address: it returns nil below 240 extracted characters, needs passwords to unlock first, and by design collides across distinct documents that share opening boilerplate.
  EVIDENCE: Sources/PDFHammerCore/Hammer.swift:924-933, guard squeezed.count >= minimumCharacters else return nil at line 928

- RunCache is a single JSON blob rewritten whole on every save, with no index, and is explicitly documented as disposable rather than authoritative.
  EVIDENCE: Sources/PDFHammerCore/Cache.swift:1-38, doc comment lines 3-7 ('a preview, not a claim about the present'), saveRunCache atomic full-file write at line 37

- Application Support is resolved via FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask).first, appending a 'PDF Hammer' folder — the exact call the new store should reuse.
  EVIDENCE: Sources/PDFHammerCore/Cache.swift:22-28 and Sources/PDFHammer/AI.swift:14-17 (same pattern, used for the API-key file)

- The app carries no entitlements file anywhere in the repo, confirming it is non-sandboxed, so that FileManager call resolves to ~/Library/Application Support/ directly, not a sandbox container.
  EVIDENCE: find over the repo for *.entitlements returned nothing (checked via Bash, 2026-08-27)

- Search.swift's search is entirely in-memory and per-run: Searchable is built fresh from an in-memory Item, and matches() does a byte-level substring scan with no persisted index; a 'text:' query can only be satisfied if the document's text was already read into memory for this run.
  EVIDENCE: Sources/PDFHammerCore/Search.swift:111-131 (Searchable init, text is nil 'until the document's text has been read'), 150-174 (matches, case "text": ... ?? false)

- FolderWatcher wraps FSEvents (FSEventStreamCreate/SetDispatchQueue/Start) with file-level events, a 1.0s FSEvents latency, and an additional 1.2s software debounce, then calls a single no-payload onChange() closure — it tells the caller 'something changed', not which files.
  EVIDENCE: Sources/PDFHammer/Watcher.swift:9-19 (settle: TimeInterval = 1.2), 36-53 (FSEventStreamCreate with kFSEventStreamCreateFlagFileEvents, latency 1.0), 66-73 (changed(), debounce)

- Marks and notes live inside the PDF file itself as standard PDFKit annotations (highlight bounds/quads, .color, .contents), not in any side file or database; saving re-serializes the whole PDFDocument through a temp file and an atomic FileManager.replaceItemAt.
  EVIDENCE: Sources/PDFHammer/Annotations.swift:156-195 (highlightSelection creates a PDFAnnotation and calls page.addAnnotation), 198-230 (setColour/remove/setNote mutate the live annotation then call save()), 245-261 (save(): temp file + replaceItemAt)

- markdownNotes/markdownCatalogue/markdownBibliography are on-demand export formatters over in-memory values; there is no persisted Markdown store or extracted-body concept in the codebase today.
  EVIDENCE: Sources/PDFHammerCore/Markdown.swift:40-123 (pure functions, no file I/O, no caching)

- The macOS SDK ships a system Clang module named SQLite3 that wraps sqlite3.h and declares 'link "sqlite3"', so `import SQLite3` in a Swift file compiles and auto-links against the system libsqlite3 with zero third-party dependency.
  EVIDENCE: MacOSX26.5.sdk/usr/include/SQLite3.modulemap: 'module SQLite3 [system] { header "sqlite3.h" ... link "sqlite3" }'; registered in the SDK's top-level module.modulemap as 'extern module SQLite3 "SQLite3.modulemap"' (checked via Bash find/cat, 2026-08-27)

- This was confirmed by actually compiling and running a standalone Swift script that opens an in-memory DB, creates a table, and inserts a row via sqlite3_open_v2/sqlite3_prepare_v2/sqlite3_bind_text/sqlite3_step, all through `import SQLite3` with no package dependency.
  EVIDENCE: ran `swift <script>.swift` locally; output 'SQLite3 imports fine', 'open rc=0', 'bind rc with unsafeBitCast workaround = 0', 'done' (2026-08-27, this session)

- SQLITE_TRANSIENT is defined in the header as a cast macro ((sqlite3_destructor_type)-1), which Swift's Clang importer does not bridge into a usable Swift symbol; code must define its own `let SQLITE_TRANSIENT = unsafeBitCast(-1, to: sqlite3_destructor_type.self)`.
  EVIDENCE: MacOSX26.5.sdk/usr/include/sqlite3.h:6353-6355 (#define SQLITE_TRANSIENT ((sqlite3_destructor_type)-1)); confirmed by compiling `let x = SQLITE_TRANSIENT` after `import SQLite3` and getting 'error: cannot find SQLITE_TRANSIENT in scope' (this session)

- The system libsqlite3 (version 3.51.0, matching sqlite3.h's SQLITE_VERSION) is compiled with FTS3, FTS4, FTS5 and RTREE enabled.
  EVIDENCE: `sqlite3 :memory: "pragma compile_options;"` output includes ENABLE_FTS3, ENABLE_FTS4, ENABLE_FTS5, ENABLE_RTREE (this session); sqlite3.h:  #define SQLITE_VERSION "3.51.0"

- FTS5 external-content tables work correctly against a source table with a TEXT PRIMARY KEY (SQLite still gives it an implicit integer rowid unless declared WITHOUT ROWID), including staying in sync across INSERT/UPDATE/DELETE via the standard trigger pattern.
  EVIDENCE: local sqlite3 CLI test this session: created `documents(content_hash TEXT PRIMARY KEY, ...)` plus `documents_fts USING fts5(..., content='documents', content_rowid='rowid')` with ai/au/ad triggers; inserted two rows, matched correctly, updated one row and the match followed the update, deleted a row and its match disappeared

- FTS5's built-in bm25() ranking function is available and returns lower (more negative) scores for better matches, usable directly in ORDER BY with no custom scoring code.
  EVIDENCE: local sqlite3 CLI test this session: `SELECT rowid, body, bm25(t) FROM t WHERE t MATCH 'strange loops' ORDER BY bm25(t)` returned the row with more term occurrences at a more negative (better) score

- WAL mode is SQLite's documented, native mechanism for exactly the constraint this task names: one writer and multiple readers, in different processes, running concurrently without blocking each other, as long as all processes are on the same host (not a network filesystem).
  EVIDENCE: https://www.sqlite.org/wal.html — quoted: 'WAL provides more concurrency as readers do not block writers and a writer does not block readers.'; 'However, since there is only one WAL file, there can only be one writer at a time.'; 'All processes using a database must be on the same host computer; WAL does not work over a network filesystem.'

- Confirmed locally that enabling WAL mode and creating an FTS5 table both work against a real file-backed database with the system sqlite3, producing the expected -wal/-shm sibling files.
  EVIDENCE: local test this session: `sqlite3 probe.sqlite "PRAGMA journal_mode=WAL; CREATE VIRTUAL TABLE docs_fts USING fts5(...); ..."` printed 'wal' and a working FTS match; `ls` showed probe.sqlite, probe.sqlite-shm, probe.sqlite-wal

- The system libsqlite3 build reports itself as 'Multi-thread' safe (sqlite3_threadsafe() == 2): distinct connections may be used concurrently on distinct threads, but a single connection must never be entered by two threads at once.
  EVIDENCE: ran `print(sqlite3_threadsafe())` after `import SQLite3` this session: printed 2; also `pragma compile_options` showed THREADSAFE=2

## Risks

- Annotating a PDF rewrites its bytes (Annotations.swift:245-261), which changes its content_hash under a pure content-addressed scheme — without the proposed superseded_by/carry-forward step, every highlight a user makes would silently orphan that document's tags, project membership, and notes.

- The supersede heuristic (same path, new hash, matching page_count/title/author ⇒ same logical document) is a heuristic, not a guarantee, and could misfire on a document that was both re-annotated and structurally edited between watcher passes.

- WAL mode requires all processes to be on the same host and does not work over a network filesystem (verified via sqlite.org); Application Support is local today, but if the database is ever relocated under an iCloud-synced or network-mounted folder, cross-process concurrency silently breaks.

- The system libsqlite3 build reports sqlite3_threadsafe()==2 (multi-thread, not serialized): a single connection must never be entered by two threads concurrently. The actor-per-connection design enforces this, but any future code path that reaches the raw OpaquePointer off-actor (easy to do by accident given Hammer.swift's existing heavy use of DispatchQueue.concurrentPerform) would be undefined behavior, not just slow.

- FTS5 external-content tables only stay in sync via the maintenance triggers firing on every row-level INSERT/UPDATE/DELETE; any future bulk operation that bypasses them (a schema migration that recreates a table, a raw bulk load) will desync the index silently until an explicit rebuild is run.

- Whole-document Markdown extraction (walking every page of every PDF with PDFKit's PDFPage.string) has not been benchmarked at library scale in this codebase; the only precedent, openingText, deliberately reads just 3 pages and caps at 4000 characters, so its cost profile does not establish the cost of full-document extraction across thousands of documents.
